## Последний ежедневный запуск

Последний проверенный scheduled daily — [41395554460](https://github.com/Floppa2003/key-privileges/actions/runs/41395554460), **2 ноября, 05:42–06:03 UTC**. Он использовал код `ec00b58f8bf0d368b89e9718875d42a4c9feeb13` и каталог из [collector run 41303920236](https://github.com/Floppa2003/key-privileges/actions/runs/41303920236), artifact `13082537497`: 1391 записей, наблюдение 1 ноября в 11:55 UTC.

Actions был зелёным, но результат — **`no_input`: 0 захваченных документов, 0 модельных запросов, 0 completed, 0 cached**. Все 27 попыток захвата получили `Page.goto: net::ERR_NAME_NOT_RESOLVED` для `https://konsierge.com/benefits`. Провайдеры были доступны по локальным ограничениям; квота не объясняет отсутствие результатов. Очередь содержала 1322 цели. Дата usage оставалась 1 ноября, поскольку её обновление происходит при входе в обработку документов, до которой этот запуск не дошёл.

Старый выбор сортировал всю очередь по `last_checked`, заранее брал первые `max_pages` и последовательно расходовал мягкий бюджет 1200 секунд. Большая группа новых целей одного origin оказалась впереди остальных. **Это наблюдение об ошибке DNS в том runner, а не утверждение о текущей доступности сайта.**

Исправление очереди чередует origin фактических capture URL, сохраняя порядок по возрасту внутри каждого. Группировка выполняется для всей очереди до ограничения числа попыток; `max_pages` считает реальные попытки захвата. Не достигнутые из-за бюджета цели не получают нового статуса или `last_checked`, их прежние результаты сохраняются. Ошибка разбора одного старого URL изолируется, а не обрывает группировку всей очереди. Полные тексты, все изображения, проверка manifest и ограничения модельных каналов сохраняются. Это исправляет распределение работы, а не DNS внешнего сайта.

Отдельная блокировка origin по тексту DNS-ошибки намеренно не добавлена: ошибка `Page.goto` может возникнуть после redirect на другой host, до существующей проверки origin. Само чередование устраняет наблюдённую монополию одного сайта без недостоверного вывода о том, какой host не разрешился.

## Что изменено в контракте

- Самостоятельное `benefit_text`, обязательный `value_qualifier` (`exact`, `up_to`, `from`, `null`) и `program_restrictions` сохраняют качественные выгоды, различия ставок и страницы только с правилами.
- Раздельные компоненты, их аудитория, исключения, география и сноски описаны явно. Внутреннее вознаграждение персоналу не должно становиться клиентской скидкой.
- Размер получаемой выгоды отделён от цены покупки. Бесплатный подарок при пороге основного заказа остаётся подарком; предмет, за который платят специальную цену, не превращается в бесплатный подарок.
- При противоречии применимых конечных дат требуется `valid_until=null`. Упоминание конфликта в `unknowns` само по себе не разрешает выбрать позднюю дату.
- Вторая редакция не ослабляет JSON Schema: после удаления descriptions и нормализации порядка required валидационные ограничения совпадают. Инструкции повышают определённость контракта, но не гарантируют его семантического соблюдения моделью.

## Проверки кода и состояния

На коде второго прохода GitHub CI выполнил **1576 Python-тестов, 4 сценария настоящего Chromium и 7 KEY-тестов**, все успешно: [run 41418659940](https://github.com/Floppa2003/key-privileges/actions/runs/41418659940). Реальный отклонённый Four Seasons из первого прохода содержит ровно четыре пропущенных обязательных квалификатора; схема не была ослаблена и автоматического ремонта JSON не было.

Для исправления очереди добавлены [8 регрессионных сценариев](tests/test_merchant_capture_fairness.py). Тест с 27 недоступными целями одного сайта и бюджетом в пять попыток получает порядок `a01, b1, a02, b2, a03` и два успешных захвата другого сайта. Проверены FIFO/возраст внутри origin, реальный URL захвата, нормализация порта, некорректные старые URL, лимиты попыток и времени, сохранение не достигнутых записей и отказ при повреждённом manifest. DNS-ошибки после redirect не приводят к пропуску соседних целей. Новые границы сначала воспроизведены как ошибки на прежней реализации, затем прошли; существующие 16 queue-тестов также прошли. Полный итоговый Python-набор локально: **1584 теста, OK, 47,175 секунды**. Независимое ревью окончательного diff не нашло существенных замечаний. Это проверка алгоритма с подменённой границей браузерного захвата и настоящей проверкой файлов/PNG/хешей, а не утверждение о восстановлении внешнего DNS.

Для каждого из 14 запросов восстановлен request body из сохранённых payload и PNG; его хеш совпал с фактическим measurement. Проверены также ZIP, полный список файлов и каждый внутренний checksum. Состояние между проходами непрерывно: ledger до второго прохода точно совпадает с ledger после первого.

Два независимых remote readback подтвердили, что менялись только счётчики попыток/токенов, интервалы и кредитный ledger: [первый state commit](https://github.com/Floppa2003/key-privileges/commit/e9f44604bac0d74087b0ae8328bef8e03668dc2b), [второй](https://github.com/Floppa2003/key-privileges/commit/20f9f4e16a81f75b6e39bd872a1c4056063708f1). ## Открытия, нюансы и допущения

- Полный аудит 90 ответов относится к 1 ноября; более свежий ежедневный запуск 2 ноября новых ответов не дал. Эти даты и знаменатели не взаимозаменяемы.
- В исходном аудите шесть документов теряют хотя бы одну выгоду во всём JSON; в 26 документах важный факт остаётся только в evidence/advice. Категории пересекаются и не складываются в общий процент ошибок. См. [исходный аудит](SEMANTIC_AUDIT_20261102.md).
- Источники исходного результативного snapshot наблюдались 31 октября. Повтор модели на этих данных не подтверждает актуальность предложения или личную доступность клиенту.
- Два прохода — направленная диагностика известных ошибок, а не слепой benchmark. Разные примеры и размеры партий не позволяют ранжировать провайдеров.
- Результаты первого и второго проходов относятся к разным версиям контракта. Четыре не повторявшихся во втором проходе примера не объявляются повторно проверенными на финальной редакции.
- Исправление очереди создаёт шанс для других источников при отказе одного origin. Оно не гарантирует доступность всех сайтов, 300 успешных захватов или 500 успешных модельных запросов за сутки.
- К публикации по-прежнему нужен содержательный допуск: оставшиеся ошибки ресторанных привилегий, цитат и распределения условий явно сохранены. Зелёный Actions или JSON Schema его не заменяют.
